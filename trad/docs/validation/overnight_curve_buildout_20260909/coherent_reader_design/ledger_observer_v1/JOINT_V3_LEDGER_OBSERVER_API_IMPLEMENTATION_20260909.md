# Joint-v3 ledger API: implementation validation

The separately versioned API adapter exposes original ledger-verified forecasts through its own schema. The existing producer, its health projector, all registered studies and the running dashboard remain unchanged. The handler integration is a reviewed external draft with a configuration-hash placeholder; it has not been routed or reloaded.

Final validation: **26 API cases plus 5 handler-draft cases passed** (31 total, 18.33 seconds reported by pytest). Independent source review found no remaining blocker. The adapter pins its configuration, original registry and activation, selected-v3 identity, original 20 study files and its own three-file source closure. A single-flight cache retains canonical report bytes for 15 seconds, with source/identity rechecks on every response and an original-observation age limit of 90 seconds. Original ledger/forecast/read/issue/H1/news clocks are never rewritten. Current target eligibility and the actual consumer clock are emitted separately. A detected integrity failure clears the cache and invalidates both cached and refreshing requests already in progress.

The final actual read at **08:38:49.155666 UTC on September 9** exposed **66 current original forecasts from 68 verified ledgers** while the producer envelope was actually in **generation_mismatch**. The producer reported **12 cumulative errors** and zero heartbeat-publication errors, retained separately. First call: **1.125 seconds**; cached call: **0.250 seconds**, with the same immutable report hash and separately sampled response clocks. This establishes availability of ledger evidence through the adapter, not fresh training-input readiness, numerical accuracy, profitability, execution eligibility or valid original transport.

The original producer mismatch remains a real defect. The observer neither changes the frozen producer nor accepts its bad heartbeat. Cached ledger proof remains dated to its original read; append-only ledger activity or corruption after that read can only be detected by a subsequent scan. No current-database immutability claim is made.

Use `dashboard_handler_utf8_draft.patch` for parent review. It adds `/api/joint-v3-ledger-observation` and a compact separate namespace to `/api/main` and `/api/state`, outside their existing state cache. It preserves old producer/projector and main-state-building functions. The parent must supply a reviewed specification file and its exact hash before deployment. Missing configuration remains unavailable. No frontend files were changed.

Earlier evidence is preserved: initial API failures exposed an absent compact-arm forecast_id and were fixed by using original decision ID, forecast SHA and cohort ID; the draft-test decoding failure was corrected with explicit UTF-8 without changing the original dashboard; parent review found and closed the final cached-reader generation race.
