# Joint-v3 original-outcome reassessment plan

The original `program_assessment_20260909T0316Z/performance/assess_v3.py` is suitable for a fresh assessment without changing the model, ledger, arithmetic or prior evidence. This document is a source review and execution plan. No fresh joint-ledger assessment was run for it.

The original helper starts a SQLite `mode=ro` / `query_only` transaction per pair, verifies its exact contract and activation, retains a coherent logical export, and selects only decisions with original stored outcomes. It passes every retained quote to the registered scorer and reconciles selected entry and target quote IDs with original rows. Current stored scorecards are observed separately, so generation-time set differences remain explicit. The original protocol fixes H1, fresh bid/ask endpoints, four baselines, the paired price-only diagnostic and the neutral-news ablation.

All valid joint decisions share the same reference, entry and target endpoints with their two retained pre-issue comparators. These are controlled diagnostic comparisons on the same decisions; they are not separately issued independent price-family predictions or causal evidence that news helped. The existing 80-digit Decimal summary preserves direction and positive-after-spread denominators, magnitude errors, stress costs, and matched joint-minus-comparator deltas. Comparator probabilities do not exist. The joint Brier score remains a descriptive score of an uncalibrated probability.

The small wrapper should preserve the original helper and prior pure helper byte-for-byte. It should import them only after exact hash checks, set the imported helper's `HERE` to a verified fresh external directory, and run its unchanged per-pair evaluation and aggregation with one synchronous worker. Replacing only the scheduling interface with a serial executor preserves economic arithmetic while reducing contention. Merely overriding `HERE` in a parent process and retaining the original Windows process pool is unsafe: spawned children can re-import the helper with its historical output directory. The original report's four-worker bound remains an upper bound; the new wrapper receipt must state that actual concurrency is one.

Before execution, pin the original helper, prior helper, old report, exact joint-v3 registry, all twenty registered sources, and the new wrapper itself. Check them again after execution. Use a new directory under this plan's evidence folder. Existing `inputs/*.json.gz`, per-pair results and the completed performance report remain unmodified in the old folder. Preserve partial new outputs on failure and record a failure receipt; do not write a successful wrapper receipt unless the original main assessment completes and final bindings match. Flush, sync and hash newly produced evidence after completion without altering its bytes.

Preserve the original bounds: at most 512 MiB per database, 100,000 quotes, 256 forecasts, 4,096 diagnostics, 128 MiB of quote/forecast payloads per table, and a 20-second SQL progress budget per ledger. The latter does not bound later pure scorer CPU time. This source-only review has not measured whether every current database still fits these bounds. Refuse and report any exceeded bound rather than silently truncate evidence or widen a policy.

Retain the original full valid-set summary first. A separate descriptive dependence supplement can then report, for each original comparator, all joint-versus-comparator side combinations including neutral rows, paired direction agreement, same-denominator net and MAE deltas, and clock/pair counts. Join only by the original decision identity and exact economic endpoints. The already implemented within-pair nonoverlapping-window count is a clock descriptor, not an effective independent sample size. Any signed prediction/error correlation would additionally need original retained forecast values from the hashed logical exports; the compact joint score omits signed predicted magnitude, so it must not be reconstructed from absolute error.

The study shares currencies, market factors, overlapping H1 windows, price inputs and news context across rows. No threshold or winning subset should be selected from these outcomes, and no significance, calibrated confidence, account P&L, broker fill or predictive-edge claim follows from row counts. Source and outcome clocks remain actual and per-database; this cannot be described as a globally atomic snapshot or a matched historical before/after experiment.

Execute only after the parent confirms that the current CPU-intensive pilot evaluation has finished. This plan itself has read source files and prior artifact hashes only, and has made no database, runtime, broker, model or registration changes.
