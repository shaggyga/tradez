# Repaired-news input and ledger integration

The new `oanda_causal_forecast_inputs_joint_news_v2.py` and `oanda_causal_forecast_ledger_joint_news_v2.py` accept independently replayed repaired publication output in a separate source-bound cohort. The original adapter, ledger, producer, numerical model, scorer, registrations and retained databases were not edited by this work. No worker was registered, activated or started by this implementation subtask.

The adapter retains the original v165 classification, v164/v165 historical members, governed mapping visibility, 48-hour historical window and exact real M1/H1 feature/label timing. It consumes `local_news_sentiment_repair_v1/current_news_v1.json` and verifies the repaired producer's exact seven-source closure, complete retained source evidence, original member admission and snapshot replay. Its own closure is 15 files; the worker's complete closure is 20. The unchanged old producer remains explicitly bound because its pure clustering and member interpretation are reused. No changed implementation is disguised under an old source hash.

The pair capture and shared news schemas are distinct v2 identities. The ledger's fixed dispatcher calls the new adapter, with no monkeypatch or old-module replacement. Quote observation, attempt, actual computation, issue, committed publication, independent consumption, later executable entry and original H1 target rules remain unchanged. Capture, result and emitted forecast evidence explicitly keep research enabled and all order, promotion, authorization, account and proof flags false. Old ledgers are refused before opening a writer because their immutable contracts differ.

The old 5,000-row history bound had become an operational blocker. A read-only pinned transaction at 19:42:38–40 UTC found 5,501 mappings and exactly 5,501 unique events, containing 55,778,610 raw payload bytes. There were no duplicate mappings to remove and no hash, visibility or contract mismatches. The actual mapping table makes event identity its primary key.

The new reader traverses the complete selected 48-hour history in pages of 128 rows. It validates every original wrapper hash, member version, unique event identity and mapping availability before retention. Limits are explicit: 10,000 rows, 128 MiB aggregate raw wrappers, 1 MiB per wrapper, 20 seconds per history read, 16 MiB canonical shared capture and 8 MiB compressed shared capture. Any exceeded limit withholds the complete capture; it never truncates a tail or creates a partially authorized history. Sealed diagnostics expose actual row, raw/compact byte, duration and limit values in the shared capture, pair capture and computation result.

At 19:48 UTC, the complete reader retained 5,509 original events in 4.234 seconds: 55,855,026 raw bytes became 9,851,953 compact bytes and 2,171,715 bytes when compressed. The preceding 24 hours contained 2,888 mappings and the older 24 hours 2,621. This is a rolling 48-hour window, so it does not accumulate every prior day indefinitely. Future arrival rate and article size are not guaranteed; the canonical shared-byte ceiling is the nearest capacity constraint and remains visible.

The first complete producer/history/cache benchmark fit within the existing shared limits, but exposed redundant cache work: 68 calls had median 0.556 seconds and p95 1.094 seconds. Three changing database signatures correctly caused three separate observed captures during the roughly 60-second check. That complete slow record is preserved.

The optimized implementation skips only repeated canonical serialization/hashing of private immutable bytes that already passed full hash, source and replay validation. It still checks file identity/signature and current source bindings; changed bytes receive full validation. Every caller receives a separately decoded object, retains the original observation clock and undergoes freshness/expiry checks. Concurrent misses are serialized so multiple pairs cannot independently ingest the same generation at once. Cache keys include current path/signature, history database and WAL signatures, and storage root.

The optimized complete benchmark retained 5,508 historical events plus the repaired current wrapper in **13,255,965 canonical bytes (79.0% of 16 MiB)** and **2,393,616 compressed bytes (28.5% of 8 MiB)**. All 68 subsequent requests reused one capture and one history read; median access was 0.212 seconds and p95 0.235 seconds. Total time including fresh producer work and initial validation was 26.06 seconds. These are bounded engineering timings, not a sustained throughput or uptime guarantee. Any later producer source hardening requires a newly bound observation; the original benchmark source hashes and exact clocks remain in their JSON records.

Validation passed 231 focused cases in 34.36 seconds. Tests include complete ingestion beyond the former 5,000-row limit, corruption beyond that former boundary, capacity refusal, duplicate visibility rejection, a concurrent writer against a pinned read transaction, actual temporary news SQLite capture and replay, original availability/expiry, source and shared-file tampering, concurrent cache misses, immutable old-ledger refusal, strict inert flags and actual capture/fit/publication/consumer/entry/H1 scoring for EUR/USD, EUR/JPY and EUR/HUF. The numerical model and exact evaluator are unchanged; these tests make no claim of improved accuracy or profitability.
