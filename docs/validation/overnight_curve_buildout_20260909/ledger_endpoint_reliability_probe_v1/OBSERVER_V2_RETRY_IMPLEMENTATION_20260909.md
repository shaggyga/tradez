# Bounded observer V2 retry candidate

This candidate makes a second read-only attempt for an eligible transient ledger failure after the first pass has visited every pair it can within the original eight-second deadline. It creates no forecasts, changes no original forecast clocks, and is not active routing or a new model cohort.

The first pass remains sorted by instrument and capped at 0.25 seconds per ledger. An attempted pair may receive one fresh retry capped at 0.5 seconds and the remaining original budget. Unvisited pairs are never retried. A successful ledger read with no publication or an elapsed original target is not a retry candidate.

Eligibility is narrow: an explicit SQLite BUSY or LOCKED primary code, an INTERRUPT with actual deadline exhaustion, or the original pair-time-budget reason with actual deadline exhaustion. Every eligibility decision also requires valid original clock evidence. Missing files, unknown SQLite failures, corruption, identity/hash/activation failures and successful unavailable rows cannot trigger a retry. The original 0.05-second SQLite connection timeout is unchanged.

Each retry opens a new read-only transaction and repeats the original committed-publication, consumption, activation, contract and reference-row checks. The failed attempt's row is never used as evidence. Original reference, issue, publication, consumption, news and H1 target clocks remain unchanged. All visible forecasts are rechecked at aggregate completion, including first-pass successes that expire while another pair is retried.

The report retains first-pass failures, bounded per-attempt actual wall/monotonic times and clock traces, explicit retry eligibility, SQLite primary codes, skipped retries, unique verified-pair counts and separate recovered-ledger versus recovered-forecast counts. A successful retry therefore does not erase the earlier failure. Each report remains bounded to two MiB. The eight-second budget applies to ledger scheduling and queries; mandatory before/after source and envelope reads retain the original V1 scope, and actual total elapsed is reported separately.

New sticky observation-wide wall and monotonic guards reject clock discontinuities across attempts, pairs and mandatory source reads. They return actual valid samples unchanged. Detected clock-integrity failures reject the observation; the API clears cached evidence. No values are retimestamped or reconstructed.

The new modules are `oanda_joint_v3_ledger_status_observer_v2.py` and `oanda_joint_v3_ledger_observer_api_v2.py`. The observer's closure includes its own source, the accepted V1 observer and the unchanged immutable-summary boundary. The API adds its own source. The original twenty-source joint-v3 closure and original model/cohort identity are unchanged. Every existing V1 observer verification helper has the same AST in V2. API functions/classes, including single-flight and integrity-generation cache handling, also have identical ASTs; only the observer import and version/schema constants change.

Focused tests use disposable fixtures, including an exact retained original forecast in a new read-only ledger. They cover successful-path V1/V2 row equality, fresh second transactions, deadline/chronology boundaries, classified transient errors, integrity errors, source changes after retry, immutable cached reports and native target expiry. Initial harness failures and the pre-wall-continuity test/source snapshot are retained separately. The final source-bound JSON receipt identifies the accepted test XML and review.

The candidate does not modify V1 source, its API configuration, the handler, HTML, active workers, registered model sources or runtime outputs. A prepared one-shot helper can make an explicit current read-only candidate observation into a new external evidence directory. A single successful observation would establish implementation behavior at that time, not a measured ongoing reliability improvement, current input readiness or trading performance.
