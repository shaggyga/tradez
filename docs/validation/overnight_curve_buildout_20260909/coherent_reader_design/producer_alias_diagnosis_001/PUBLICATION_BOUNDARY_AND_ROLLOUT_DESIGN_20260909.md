# Confirmed summary publication mutation

The retained ten-minute observer recorded 555 coherent and 45 unavailable observations. All 45 unavailable heartbeat hashes are reproduced exactly by changing only one existing summary field from `last_attempt.reason = building` to `published`, while preserving its old payload seal. The three groups concern CHF_ZAR (15 samples), EUR_PLN (17) and GBP_JPY (13). Every actual summary file retained by the observer has a valid original seal; the invalid hashes name mutated in-memory objects that were never written.

The frozen v3 source assigns the live attempt dictionary directly into the summary at line325, mutates that dictionary in `finish_work` at line419, then hashes `self.summary` for a later heartbeat at line518. The extracted original methods reproduce success, abstention and exception mutations with an immutable fake file sink. Joint v1/v2 and price-only pair v2 contain the same source chain. Pair v1 copies scalar attempt values, so this specific defect was not found there. Static exposure is separate from proven runtime failures.

The new unregistered `oanda_immutable_summary_publication_v1.py` has 40 passing focused tests. It seals no new timestamps or payloads: it validates the existing seal and retains detached canonical bytes; accepts publication acknowledgement only for exactly matching readback bytes; and derives heartbeat hashes/counts from those admitted bytes. A failed writer/readback must leave the caller's previous acknowledged snapshot in place. The module performs no I/O, imports no worker/ledger and samples no clocks. Counts describe the original snapshot, not refreshed target eligibility.

One retained 245,994-byte /68-pair envelope took a median 143.25ms for the complete pure freeze→readback-verification→heartbeat chain over30 iterations. This excludes actual filesystem publication and any ledger queries.

## Rollout choice A: a newly registered v4 producer

Add the immutable boundary to a new worker/source closure and new cohort registration. Preserve every v3 source, registration and ledger. The new worker must serialize exactly `FrozenSummary.raw`, atomically replace its own summary file, independently read it back and sample completion, then assign the returned `PublishedSummary`. Its heartbeat uses that object; no digest or count comes from mutable live slots. Retain failed-publication diagnostics and old acknowledged bytes. Verify ordinary summary/HB phase differences remain correctly handled by readers.

This repairs the producer itself, but a new cohort produces new prospective forecasts and duplicates capture/fitting/ledger work while v3 outcomes mature. Old predictions cannot be relabeled as v4. Numeric model/feature code and original clocks can remain byte-identical, yet new source bindings and activation mean new evidence identity. Deployment, new68-ledger activation, supervision, schema integration and forward tests are required. No rollout occurred here.

## Rollout choice B: an independent read-only v3 ledger observer

For the immediate operational coverage problem, this is the less disruptive path. A separately named observer with its own source closure/schema reads the original v3 registry and activation receipts, verifies their hashes/contracts/source/dependency identities, and opens each fixed ledger using SQLite `mode=ro` and `query_only`. In one bounded read transaction per pair, verify contract/activation plus the actual committed forecast, publication, consumer and reference-quote join. The original frozen `verified_publication` checks can be reused only through an explicitly bound read-only proxy or exact reviewed extraction; never instantiate the writer ledger class. Preserve forecast IDs, cohort, issue/reference/H1 target and original publication/consumption times, and record new observer-read completion separately. Recheck actual target remaining time for visibility.

The observer must publish an explicit `observer` identity and `origin_study = v3`; it cannot mark the old mismatched heartbeat valid or count the same forecast as a new prediction. An independent ledger proof is required; a payload-sealed old summary alone is insufficient. Source/contract errors, absent receipts, future clocks or expired H1 targets remain unavailable. Original news expiry is checked at issue as registered; a previously valid H1 forecast is not retrospectively erased when current news ages. Current input readiness is a separate observation: it must be reported unavailable or as a dated durable attempt unless independently supported. Keep old producer errors visible.

This path adds approximately68 bounded read transactions per chosen cycle, plus source/envelope work, and no model fits or new forecast ledgers. Its actual CPU/SQLite lock cost has not been measured here. Start with latest joined publications only, fixed paths/query bounds and actual per-pair observation clocks; avoid full quote/history scans or lifetime table counts. Source/activation tamper, concurrent commits, missing receipts, duplicate identities, original-clock preservation, stale targets and immutable publication all need adversarial fixtures plus a bounded live read-only acceptance. The observer must never silently substitute its output under the original v3 producer schema.

The frozen sources and active processes are unchanged. The helper is tested but unbound and unactivated; rollout remains a separate decision.
